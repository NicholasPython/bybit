# Bybit 自动交易系统需求自评报告

评审轮次：第 1 轮  
评审对象：[需求文档 v0.1](requirements.md)  
评审方式：作者自审、独立工程审查、独立期权/账户语义审查、官方接口核对、文档结构检查。  
评审结论：**有条件通过，可进入开发拆解；实盘就绪条件尚未满足。**

## 1. 结论与评价范围

需求已明确用户确认的范围：代码规则或定时策略，现货默认不借贷，期权只买入开仓与卖出平仓。文档包含 45 条编号需求、28 个验收场景、8 项待确认事项，并将只读、模拟、非实盘联调、人工看守实盘验证与无人值守运行分阶段处理。

本轮发现并修订 13 项需求问题，其中 2 项为 P0、8 项为 P1、3 项为 P2。这里的“已修订”仅表示文档中的规则和验收要求已补齐，不表示功能已经实现或测试通过。本轮没有访问用户交易凭据、连接用户账户、部署服务或执行交易。

评审严重度与需求优先级分别使用：本报告 P0 表示可能直接误导关键风控实现、需要立即修订的文档缺陷；P1 表示必须在相关模块设计定稿前消除的执行/账务歧义；P2 表示影响边界理解、可验证性或阶段安排的问题。

## 2. 自我评价

| 维度 | 判断 | 依据与实际限制 |
|---|---|---|
| 范围清晰度 | 通过 | 区分用户确认、设计假设和待确认项；卖方、多腿、借贷、AI 决策及高频交易明确不在首期范围。具体第一条实盘策略仍待用户定义。 |
| 需求可追溯性 | 通过 | 45 条需求都有验收场景引用，编号无重复；包含操作状态、数据实体和阶段交付物。编号覆盖不代表每个子条件都已具备详细测试脚本。 |
| 交易执行可靠性 | 文档层面通过 | 明确超时未知、成交去重、撤单竞态、资金预留、单执行者、重启对账和恢复证据。需通过故障注入验证实际实现。 |
| 期权与资金语义 | 修订后有条件通过 | 补齐结算币现金、双侧 Delta、策略持仓归属、禁开仓窗口旧挂单及到期预算释放。数量/Greeks 单位和账户能力仍须实际验证。 |
| 账务与风险口径 | 修订后有条件通过 | 统一权益估值、外部资金流调整、成本分摊、日初基线与回撤高点。具体估值源、币种、容差和资金限额未定。 |
| 运维可执行性 | 有条件通过 | 定义暂停/恢复、外部监控、备份恢复、时间同步和无人值守门槛。监控渠道、部署环境及恢复时长目前没有实测证据。 |
| 首期规模 | 可控但需按阶段交付 | 模块化单体、单账户单执行者与低频容量合理；账本和恢复逻辑工作量显著，不能把它估算成只有几个下单接口的脚本。完整前端和高级分析不应挤占执行可靠性工作。 |
| 实盘就绪度 | 未满足 | 无已实现程序、无账户能力报告、无验收执行记录、无经用户确认的交易和资金配置。不能把需求审查结论作为启动实盘的授权。 |

最主要的优点是将“交易系统正确运行”转成了可观察的状态和验收条件。最主要的不足是具体交易策略与实际账户证据仍缺失，因此当前可以准确拆解基础设施和执行闭环，不能准确评估策略收益、真实成交质量或全部开发工期。

## 4. 本轮实际完成的检查

- 检查文档与用户确认范围一致，保留推荐假设和未确认事项的状态。
- 独立审阅订单、预留、持仓、暂停恢复、期权及账户语义，交叉合并重复发现。
- 核对关键官方接口规则：期权减仓参数、异步下单、合约规格、Demo 环境、账户余额及自动借贷机制。
- 静态检查需求编号唯一性、验收编号唯一性、需求到验收的引用覆盖、Markdown 表格列数、代码块及本地链接。
- 对修订位置进行回读，确保报告中的问题确实已反映到需求与验收条件中。

本轮未执行：应用单元测试、交易所接口联调、服务器压测、账户权限测试、故障恢复演练、真实交易或策略收益回测。45/45 的编号覆盖只能说明文档引用完整，不能表述为“系统测试通过”。

## 6. 建议的开发起点

先实现环境与身份校验、数据库模型、只读行情/账户同步，再实现可重复的 Paper 适配器、资金预留和订单恢复状态机。首批自动化验收应优先覆盖 AC-07～AC-13、AC-15～AC-18 以及 AC-27：这些场景直接决定是否会重复买入、错误释放资金或超额平仓。

完成上述闭环后再完善管理页面和非实盘联调。实施过程中若发现接口能力与文档不符，应修订能力矩阵和对应需求，不能绕过不支持的减仓、身份或资金检查来获得“成功下一笔单”的结果。
